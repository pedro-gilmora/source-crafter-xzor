**Goal:** A `Model` base class for xzor apps: plain TypeScript classes whose fields track their own changes (state, originals, revert, confirm, changes to send), validate themselves, notify listeners as an `EventTarget`, and re-render the xzor components that display them, with no Vue and no per-instance closures.

## Decisions for you (approve or change before work starts)

Revised after review: tracking is what a model *is*, so there is no per-field decorator; fields become tracked at compile time.

1. **Compile time: every field of a model becomes a `#private` slot with a getter and setter.** You write plain fields:
   ```ts
   import { Model, Validate, Persist } from "@source-crafter/xzor-runtime/model";
   export default class Worker extends Model {
     name = "";
     @Validate(validNumber) hours = 0;
     @Validate(validNumber) tax = 0;
     @Persist get payment() { return this.hours * this.tax; }
   }
   ```
   When the bundle loads a project `.ts`, each class that extends `Model` (imported from the runtime) gets every instance field rewritten as a standard auto-accessor with the tracking decorator: `@__track accessor hours = 0`. That is exactly a `#private` field plus a getter and setter on the prototype, generated by the language: no closures per instance, initializers and types untouched. `static`, `#private`, `declare`, `readonly` and methods/getters are left alone; `@Validate`, `@Ignore` stay where they are and now decorate the accessor. The type checker and the editor keep reading your original source (same types), the bundle gets the rewritten one; only columns on those field lines shift in source maps (lines stay exact).
   - **Marker:** `extends Model` alone (it also gives the types: `hasChanges`, `revertChanges`, ...). A `@Model` class decorator can be accepted as an alias marker, but TypeScript can't add members from a decorator, so `extends Model` is needed either way. Recommended: `extends Model` only.
2. **What a template reference does (your question).** Nothing extra is generated in templates. The generated getter is the subscriber: while a component renders, reading `worker.hours` (directly in markup, in an `@if`, inside `payment`'s getter, anywhere) records "this component shows `worker`'s `hours`". The component then has one `change` listener on `worker` (the model is the `EventTarget`), filtered to the properties it read. Precise and automatic:
   - a setter called from anywhere (a service, a timer, a WebSocket message, another component) dispatches `change` → the components that read that property re-render, once per microtask;
   - a related property: `payment` reads `hours` and `tax` through their getters, so a template showing `payment` re-renders when either changes;
   - a manual `worker.dispatchEvent(new ModelChangeEvent("hours", ...))` re-renders the same components;
   - an event handler that changes the model re-renders its component once (the handler's own re-render and the change are merged).
   - *Why not generate subscription statements in the templates:* the template compiler has no types, so it can't tell a model from any other object, and paths inside `@for` are dynamic; recording on read is exact and costs one `if` in the getter outside renders.
3. **Package shape:** `@source-crafter/xzor-runtime/model`, a separate entry; apps without models keep a byte-identical bundle.
4. **API renames:** `$$` becomes `state` (same `State` values: Detached 1, Unchanged 2, Added 4, Deleted 8, Modified 16); `(n).on()` becomes `hasState(flags)` (xzor never patches built-in prototypes); `isLike` becomes an exported function; `trackChanges(array)` becomes `class EntitySet<T extends Model> extends Array<T>`; `@Unwatch` becomes `@Untracked` on the rare field that must stay a plain field.

## Architecture

- `runtime/model.ts`: `Model extends EventTarget`, the internal `__track` accessor decorator, `@Persist`, `@Ignore`, `@Untracked`, `@Validate`, the validators, `isLike`, `State`, `ModelChangeEvent`.
- `runtime/entity-set.ts`: `EntitySet`.
- `src/bundle.ts`: `trackModelFields(src)`, next to `stripMarkerDecorators` and using the same scanner (strings, templates, comments, balanced brackets): finds `class X extends <local bound to Model from @source-crafter/xzor-runtime/model>` and rewrites each instance field declaration `[decorators] name[?!][: T] [= init];` to `[decorators] @__track accessor name[: T] [= init];` (adding the `__track` import). Applied to project `.ts` files only, like the marker stripping.
- Decorators record per-class metadata (tracked names with an index each, validators, persisted getters, ignored names) in `context.metadata`, read once per class; nothing is stored per instance except values and, for changed fields only, their originals.
- The `__track` setter: compare with `isLike` (primitives with `Object.is`, `Date` by time, arrays and plain objects deeply, models by identity); store; record the original on the first change; move the state (Unchanged → Modified, Detached → Added, as before); dispatch `ModelChangeEvent` only if the model has `change` listeners (`Model` counts its own listeners by overriding `addEventListener`/`removeEventListener`, so a model nobody watches never allocates an event).
- `ModelChangeEvent extends Event` (type `"change"`, fields `property`, `value`, `previous`), and a `"state"` event when `state` changes.
- Reading (decision 2): the runtime exposes the component being rendered to `model.ts` through a hook it sets around `buildRenderTree`; the `__track` getter records `(model, property index)` only while that hook is set. Per component and model: one listener and a bitmask of the properties read (fields past 31 count as "any"), rebuilt on every render; models not read again are unsubscribed, all are unsubscribed on dispose. A `change` whose property is in the mask schedules the component; re-renders are coalesced per microtask and skipped if the component already rendered after the change (an event handler's own re-render counts).

## Global Constraints

- Zero npm dependencies; no built-in prototype patches.
- Apps that don't import `@source-crafter/xzor-runtime/model`: bundle byte-identical; `runtime/index.ts` gains only the renderer hook (one variable write before and after each render).
- Per instance: values, a `state` number, a lazily created originals object (only once something changes), the EventTarget's own internals. No closures, no JSON copies.
- A set with no `change` listener allocates nothing beyond the original value record on its first change.
- One render per component per microtask, however many fields change; a change to a property the component didn't read doesn't render it.
- The field rewrite never changes a line count, and a project `.ts` without a `Model` subclass is untouched (byte-identical).
- Semantics kept from the original: the five states and their transitions; `hasChanges`, `hasValidChanges`, `changes` (primitives plus changed nested models/sets; sets list only changed items), `revertChanges()`, `confirmChanges(serverValues?)`, `hasErrors`, `errors` (empty while Detached/Deleted or before the first change), `@Persist` getters marking the model modified when their value changes and being serialized, `@Ignore` fields never serialized, `EntitySet.delete` (Added items removed, others marked Deleted), `view` (without Deleted), `revertChanges`, `confirmChanges` (server `null` removes an item).
- Validators keep their signature `(value, model) => true | string`; ported: `required`, `email`, `phone`, `maxLength`, `minLength`, `requiredIdValue`, `nonZero`, `minValue`, `maxValue`, `date`.

## Review Focus

- A grid of 1000 rows bound with `@bind`: typing in one cell re-renders only that row's component (or the grid once), never all rows.
- A template showing `worker.payment` (a getter over `hours` and `tax`) re-renders when `tax` changes from a service call.
- A model class with a field named like a keyword-ish identifier (`get`, `set`, `static`, `accessor`), a field initialized with a multi-line object or arrow function, an optional field (`note?: string`), a definite one (`id!: number`): all rewritten correctly; a class extending something else named `Model` (not imported from the runtime) is untouched.
- A model shown by two components: a change from a service (no event handler involved) re-renders both, once each.
- A component that stops showing a model (an `@if` turns off) no longer re-renders when it changes; a disposed component holds no listener.
- `revertChanges()` after edits to nested models and sets restores everything and the state; `confirmChanges()` makes the current values the new originals.
- Setting a field to an equal value (same date, same array contents) changes nothing and dispatches nothing.

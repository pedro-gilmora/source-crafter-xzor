# Roadmap 3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** `@typeparam` inference, keyed type checks (ZDI12), optional disposers, directive comments, live DI diagnostics in `.ts` and `.tszor`, a persistent analyzer, an event-driven incremental `--watch`, and `.zor` empty-dir cleanup.

**Architecture:**
- The analyzer contract grows by a few fields (Task 2). The Rust graph and emitter consume them.
- A long-lived `di.ts --serve` process (Task 4) backs `zor build`, `--watch` (Task 5) and the LSP (Task 6).

**Tech Stack:** Rust 2024 (no crates), Bun 1.4, TypeScript 7 (`typescript/unstable/sync`), happy-dom.

**Spec:** [docs/superpowers/specs/2026-10-13-roadmap-3-design.md](../superpowers/specs/2026-10-13-roadmap-3-design.md). DI base spec: [2026-10-12-di-bootstrap-design.md](../superpowers/specs/2026-10-12-di-bootstrap-design.md).

## Global Constraints

- Memory and performance first: no allocation beyond what hand-written code needs. No `WeakMap`s, wrappers or extra closures in hot paths or generated code.
- No new Rust dependencies. JSON goes through `src/json.rs`.
- Analyzer `at` values are UTF-16 offsets. Rust converts them with `utf16_to_byte`.
- Diagnostics use the format `file(line,col): error ZDInn: message`.
- Generated `.zor/` files are never hand-edited.
- Verify with `cargo test`, `bun test`, `bun run test:grammar`, `cargo run -q -- build examples/counter` and `cargo build --release`.

## Review Focus

- A trailing `// comment` on `@import x from "y" // why` must not swallow a `//` inside the string (`@import x from "http://a"`). Test in Task 1.
- A key match where the parameter is a supertype of the service (interface implemented by the keyed class) must NOT be ZDI12. Test in Task 2.
- `--watch` must not loop on its own writes to `.zor/` and `dist/`. Test in Task 5.
- An edit that deletes the line holding a DI diagnostic must drop that diagnostic, not move it onto a neighbor. Test in Task 6.
- The persistent analyzer must recover when its process dies: the next request restarts it. Test in Task 4.

### Task 1: Directive trailing comments

**Files:** `src/parser.rs`, `editors/vscode/syntaxes/tszor.tmLanguage.json`, `editors/vscode/test/gen.ts` (regenerate `syntax.test.tszor`)

**Rule:** the directives `@inject`, `@inherits`, `@implements`, `@typeparam`, `@attribute`, `@import` and `@page` end their value before a trailing `//` or `@*`. Both are found outside string literals only (`'`, `"`, backtick). The value is trimmed. The comment gets a `Comment` token span. A `@* … *@` comment may continue onto following lines, as anywhere else.

- [ ] Failing tests (parser):
  - `directive_line_comment`: `@inject IDatabase db // the store` gives type `IDatabase`, name `db`.
  - `directive_razor_comment`: `@inherits Base<T> @* why *@` gives `Base<T>`.
  - `import_comment_ignores_strings`: `@import x from "http://a" // c` gives `x from "http://a"`.
  - `page_comment`: `@page "/a" // home` gives route `/a`.
  - A comment token is emitted for each.
- [ ] Grammar: the directive rules accept and scope a trailing `comment.line.double-slash` or `comment.block`. Add `gen.ts` assertions for `@inject A a // c` and `@typeparam T @* c *@`.
- [ ] Run `cargo test`, `bun editors/vscode/test/gen.ts; bun run test:grammar`. Commit as `feat: comments after directives`.

### Task 2: Analyzer contract v2, optional disposers, ZDI12, parameter positions

**Files:** `src/di.ts`, `tests/di.test.ts` (and fixture), `src/di/model.rs`, `src/di/graph.rs`, `src/di/emit.rs`, `src/build.rs` (diagnostic formatting)

**Contract additions** (all fields always present):
- `Registration.disposeOptional: boolean`. It is true when the detected disposer member is optional (`?`).
- `Param.file: string`. The project-relative file declaring the parameter: the constructor's or factory's file. For component injects, the component's `.zor` file.
- `Param.at: number`. The UTF-16 offset of the parameter name.
- `Param.badKeys: string[]`. The ids `"<provider class id>:<registration index>"` of every keyed registration, in any provider, whose `key` equals the parameter name and whose service type is NOT assignable (`checker.isTypeAssignableTo(service, paramType)`) to the parameter type. For `promise: true` params, compare against the unwrapped `T`.

**Graph:**
- When a parameter resolves by key to a registration whose origin id is in `badKeys`, report **ZDI12** at the parameter: `<param>: key "<key>" provides <Service>, which is not assignable to <ParamType>`.
- Diags gain a position override: ZDI02/05/12 for a constructor or factory parameter report at `Param.file`/`Param.at`, and for component injects keep `inject: Some(name)`.
- `Diag` gets `pub param_at: Option<(String, usize)>`. When it is set, `format_diags` uses it.

**Emit:**
- When `disposeOptional`, the release is `d0?.dispose?.()`, `d0?.[Symbol.dispose]?.()` or `await d0?.[Symbol.asyncDispose]?.()`.

- [ ] Failing tests:
  - di.test.ts:
    - `disposeOptional` for an interface with `dispose?(): void` returned by a keyed factory;
    - `Param.at` points at the parameter name;
    - `badKeys` is set for a keyed `number` injected into a `string` parameter, and empty when the keyed class implements the parameter's interface.
  - graph.rs: `zdi12_key_type_mismatch` (position = the param), and a supertype that is not a mismatch.
  - emit.rs: `optional_dispose_uses_optional_calls`.
  - build.rs: ZDI02 for a missing constructor dependency is formatted at the parameter's line and column in the declaring `.ts`.
- [ ] Spec: add ZDI12 to the DI base spec's table and to `docs/design.md`.
- [ ] Run all suites. Commit as `feat(di): ZDI12, optional disposers, parameter positions`.

### Task 4: Persistent analyzer and `.zor` empty-dir cleanup

**Files:** `src/di.ts`, `src/build.rs` (or a new `src/analyzer.rs`), `tests/di.test.ts`

**Protocol:**
- `bun di.ts --serve <projectRoot>` reads JSON lines `{ "files": [...], "components": [...], "overlays": { "<path>": "<text>" } }` and writes one Facts JSON line per request.
- The first request opens the project. Later requests call `updateSnapshot` with the files changed since the previous request: paths whose overlay text or on-disk mtime changed. Use what the sync API offers for file changes and overlays; spike it and note the calls.
- The one-shot CLI mode stays, for tests.

**Rust:**
- `pub struct Analyzer { child, stdin, stdout }` with `pub fn analyze(&mut self, files, components, overlays: &[(PathBuf, String)]) -> Result<Facts, String>`.
- It restarts once when the pipe is broken.
- `build::di` takes `&mut Analyzer`, which callers own per root.

**Cleanup:** after `prune`, remove empty directories under `.zor/`, bottom-up.

- [ ] Failing tests:
  - di.test.ts: two requests on one `--serve` process, where the second sees an overlay that adds a registration; one process across both.
  - build.rs: `analyzer_restarts_after_kill`, and `prune_removes_empty_dirs`.
- [ ] Measure the first and second request times on the DI fixture and put them in the report. The second should be well under the first.

### Task 5: Event-driven incremental `--watch`

**Files:** `src/watch.ts` (new), `src/build.rs`, `src/main.rs`

- **Watcher:** `bun watch.ts <root>` uses `fs.watch(root, { recursive: true })` and prints changed paths, one per line, relative to the root. The script is embedded like the others and written to `node_modules/.cache/zor/`.
- **Rust:** reads the lines on a thread and batches them for 50 ms. It drops paths under `.zor/`, `dist/`, `node_modules/` or any dot-dir. Per batch:
  - recompile only the changed or added `.tszor` files (`compile_one`), and delete outputs of removed ones;
  - rerun DI (through the persistent analyzer) only if a provider `.ts` changed, a recompiled `.tszor`'s inject list changed, or a `.tszor` was added or removed;
  - then type-check and bundle.
- The polling `snapshot`/`changed` loop is removed.

- [ ] Failing tests (build.rs, with a temp project):
  - `watch_batch_plan`: a pure function from a batch of paths to `{ recompile, remove, di }` decides correctly for a `.tszor` body edit (no DI), an `@inject` edit (DI), a provider `.ts` edit (DI), and an unrelated `.ts` (no DI).
  - Paths under `.zor/`/`dist/` are ignored.
- [ ] Manual check, noted in the report: run `cargo run -- build examples/counter --watch --no-bundle`, touch `Counter.tszor`, and see one rebuild without a loop.
- [ ] Commit as `feat(build): event-driven incremental watch`.

### Task 6: Live DI diagnostics in `.ts` and `.tszor`

**Files:** `src/lsp/server.rs`, `editors/vscode/src/extension.ts`, `tests/lsp.test.ts`

- **Client:** `documentSelector` adds `{ scheme: "file", language: "typescript" }`. The server tracks `.ts` documents (text plus version), answers no feature requests for them (returns null and empty results), and never proxies them to tsgo.
- **Publishing:** DI diags go to every open document they target. That is `.ts` decorators and parameters (via `Param.file`/`at`, and the registration `at`) and `.tszor` injects. Closed files get nothing.
- **Live shift:** on each `didChange` of an open document, the server shifts that document's DI ranges by the edit and republishes. A range intersecting the edited span is dropped.
- **Live reanalysis:** 300 ms after the last `didChange` of a `.ts` or `.tszor` in a DI project, run the analysis through the persistent analyzer, with all open documents' text as overlays (and the in-memory compile of open `.tszor` files), on the existing worker thread with its generation counter.
- Saves and watched-file events keep working.

  - open a `.tszor` with `@inject Missing m`, edit without saving; ZDI04 appears.

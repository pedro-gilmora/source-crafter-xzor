# Page shells: preloaded shell rendering (PSR) (backlog)

Status: built (shells, manifest, compressed copies, and the server that serves them: see design.md Server apps). [spec](../superpowers/specs/2026-10-26-run-routes-psr-design.md). Measured with a proof of concept (`target/poc-delivery/poc.ts`, scratch, not committed).

## The idea

The server renders nothing. For each `@page`, the build writes a **page shell**: the app's `index.html`, plus the page's own entry script and a `<link rel="modulepreload">` for every chunk that page imports. The server answers each route with its prebuilt shell, and the browser fetches all the page's code in one parallel round trip, then renders it.

Where it sits among the rendering modes:

| Mode | HTML the server sends | Who renders the first view | Cost per request |
|---|---|---|---|
| CSR (today's `index.html`) | one empty shell for every route | the browser, after loading the entry, then the router, then the page chunk and its imports in sequence | none |
| **PSR (page shells)** | one empty shell **per page**, listing exactly that page's chunks | the browser, after one parallel download | none (prebuilt, served from memory) |
| SSG / pre-render | the page's markup, rendered at build time | the server at build time; the JS renders again on boot | none, but per URL, and dynamic data is frozen |
| SSR | the page's markup, rendered per request | the server; the JS takes over on boot | a render per request |

Prior art: Google's PRPL pattern and the app shell model (usually one shell for every route). PSR is PRPL with one shell per page, written by the compiler from the route table and the bundle's chunk graph.

## Compared with Google's PRPL

[PRPL](https://web.dev/articles/apply-instant-loading-with-prpl) (Polymer, 2016) is a checklist: **P**reload the late-discovered resources (originally HTTP/2 **P**ush, which Chrome removed in 2022), **R**ender the initial route as soon as possible, **P**re-cache the rest with a service worker, **L**azy-load other routes.

| PRPL step | How PRPL apps usually do it | xzor with PSR |
|---|---|---|
| Preload | By hand: `<link rel="preload">` tags, or a bundler plugin, in one shared shell, so every route preloads the same set (or only the entry) | The build writes one shell per `@page` with exactly that page's chunk graph as `modulepreload`; nothing to maintain |
| Render | One app shell, then the router picks the route in the browser; optional inlined critical CSS or SSR | The page's entry imports its page statically, so the first route renders without waiting for the router; no SSR (measured: pre-rendering didn't pay off at this size) |
| Pre-cache | A service worker, usually generated by Workbox | Already there: `manifest.webmanifest` makes `xzor build` write a dependency-free `sw.js` that precaches every build output |
| Lazy-load | Code splitting configured in the bundler | Already there: `--minify` makes each `@page` and `@async` component a chunk |

What PSR adds is the per-route part of "Preload" and "Render", derived at build time from the route table and the chunk graph, so the right list can't drift from the code. What PRPL has that PSR doesn't plan: inlined critical CSS, and server push (gone from browsers; `103 Early Hints` is its successor and could carry the same preload list).

## Shape

- `xzor build --minify` (already splits a chunk per `@page` and per `@async` component) also writes `dist/pages/<route>.html` for each `@page`: `index.html` with that page's `modulepreload` list in `<head>`. Production output has no source maps.
- A route manifest (`dist/pages.json` or a generated `serve.ts`) maps each `@page` pattern to its shell, in `Bun.serve` route syntax (`"/posts/:slug"`), so one shell serves every URL of a dynamic route. Unknown paths get the plain `index.html` and the client `@notFound`.
- Each shell's entry imports its page module statically, so the page loads with the app instead of after the router. Other pages stay `import()` chunks, loaded on navigation; `@async` components stay `await import(...)` chunks, outside the preload list.
- Served with `Bun.serve` static routes (in memory, ETag, gzip or brotli done at build time). `http2: true` / `http3: true` (TLS, experimental in Bun) avoid HTTP/1.1's six-connection limit when a page has many chunks.

## Measured (proof of concept)

Blog example, `--minify`, served by `Bun.serve` from memory with gzip, measured in headless Chrome (`Bun.WebView`, CDP throttling), median of 7 runs. LCP in ms; desktop is 20 ms latency, slow 4G is 150 ms latency, 1.6 Mbps and a 4x slower CPU. "ssr" is the page shell plus the page's markup pre-rendered at build time, which `mount()` replaces on boot.

| Page | Network | CSR | PSR | pre-rendered |
|---|---|---|---|---|
| Home | desktop | 228 | **180** | 196 |
| Post | desktop | 248 | 184 | **168** |
| Tag | desktop | 232 | **172** | 176 |
| Home | slow 4G | 1516 | **1168** | 1236 |
| Post | slow 4G | 1684 | **1396** | 1652 |
| Tag | slow 4G | 1540 | 1360 | **1256** |
| Home | slow 4G, no font preload | 1164 | **708** | 736 |
| Post | slow 4G, no font preload | 1292 | **836** | 1288 |
| Tag | slow 4G, no font preload | 1456 | **1056** | 1256 |

- PSR paints the page 20-25% sooner than CSR on desktop and 25-39% sooner on slow 4G, with the same bytes and requests. The JS is done rendering 25-40% sooner too.
- PSR's first paint is 30-80 ms later than CSR's, which paints the empty shell first: the preloads compete with the CSS.
- Pre-rendering won 2 of 9 cells, by small margins, and was otherwise slower: a later first paint, about 1.2 kB more HTML per page (gzip), and a second render on boot. On an app this size, xzor renders fast enough that pre-rendering doesn't pay off.
- Fonts weigh as much as the delivery: the blog's two font preloads (about 190 kB of 220 kB) cost about 400 ms on slow 4G.

The POC did not yet test the per-page entry (it still went through the router), which should save one more round trip.

## Open questions

- Import maps (stable chunk names, so one change doesn't rename its importers) or hashed names only?
- Pre-rendered markup as a per-page opt-in on top of PSR, for content pages where text before JS matters (it would need the runtime to adopt existing DOM instead of replacing it).
